# Audit, 2026-09 (v0.13.0, the practice record)

*The whole-codebase health review for #1719, run against main at a66ee938 on 2026-09-16, the commit before v0.13.0 was tagged. Every finding below becomes an issue; when this document and the issues disagree, the issues are right.*
*Which step is live is whichever issue carries an open PR; `just status` puts them on one screen.*

## How it ran

- **Eight areas, one fresh agent each, read-only in a worktree at a66ee938:** the core in two halves (session, app and analytics; then recognition, charts, validation, profile, sort), the bridge and store, the screens in two halves, the tests, the specs and docs, and the build and harness. The bridge and store reviewer ran on Fable 5.1, the other seven on Opus 5, at roughly 60 tool calls each. They produced 83 findings and three extension notes, judged against the four questions on the issue: healthy (does the code do what the docs say, and do the tests fail when it stops), simple (one way to do each thing, and no shell logic that belongs in the core), maintainable (could someone cold pick an area up from its spec), robust (where does a failure go quiet).
- **The mechanical sweep and the mutation runs**, both by the lead: the sweep first (every wire variant and view field against its Swift mentions, the rule counts, churn since 14 August, the commits to the crash-recovery blob, and sizes: 30,667 lines of Rust in the core, 18,649 of Swift in the shell); then twelve core mutations proposed by the tests reviewer, each applied, run through `cargo test -p intrada-core` and reverted, and three Swift mutations through `just ios-test`. Results in the next section.
- **Verification:** the lead confirmed findings 3, 4 and 5 by range read, and read the three Swift lines under mutation; the synthesis pass (Fable 5.1) verified every other entry by range read or grep, and says so per entry. Three reviewer claims did not survive it and are named under Dropped.
- **Deliberately not done:** no on-device walk-through this round (decision 2b); nothing was run on a simulator except the three Swift mutation runs; no CI run history was queried. Every screen effect below is read off the code, and the hand checks are listed under Not covered.

## The findings, by cost

The order is by cost to the musician first, then likelihood. Band 1: silent loss or corruption of the musician's data on the device. Band 2: wrong on screen, the musician sees something untrue. Band 3: engineering drag, a cost every future change pays (a rule the docs state and nothing enforces, two ways to do one thing, a spec that lies). Band 4: cosmetic; nothing reached the bar in this band. Within a band the more likely comes first. A cheap fix does not raise a finding; it goes in the build order. Merged findings name the reviewer ids they absorb. Each finding's `Issue:` line names its issue: thirty were filed from this document, six already existed and carry a re-rank comment.

### Band 1: silent loss or corruption of the musician's data

**1. Swiping the item-complete sheet away throws the marks and the note away without a word**
Question 4. Verified by range read. The sheet at the end of each item in the Focus Player is a plain `.sheet` with no dismissal guard, and nothing in the app calls `interactiveDismissDisabled`; the marks, the note and the per-play tempos live in the sheet's own state, and the only exits that send anything are Save and Skip. A downward swipe returns the musician to the same item, click already stopped, with nothing sent and nothing said. Cost: silent loss of entered marks, tempos and a reflection on the reflex gesture iOS trains for a half-height sheet; likely over normal use. Fix: `interactiveDismissDisabled()` on the sheet, or treat the swipe as Skip so at least the next item starts. Tier 1. Issue: #1934. (SCREEN2-1)
Where: `ios/Intrada/Views/Screens/FocusPlayerScreen.swift:40`, `ios/Intrada/Views/Screens/ReflectionSheet.swift:96`.

**2. A chord chart line typed without bar lines disappears on save, and reopening the editor shows it gone**
Question 4. Verified by range read. `parse_chart` skips any line with no `|` in it as prose, so a chart with one bar-lined line and one without keeps the first and drops the second, and the empty-chart guard never fires; `specs/chart-to-scaffold.md:77` says unparsable tokens are surfaced, not swallowed. The edit sheet rebuilds its text from the stored structure, so the dropped line is not there to correct, and the scaffold exercises are derived from the shortened chart. Cost: silent loss of typed content; moderate likelihood for a chart pasted from anywhere else. Fix: treat a non-empty, unlabelled line without a bar line as a bar, or return a parse error naming the line. Tier 2. Issue: #1935. (CORE2-1)
Where: `crates/intrada-core/src/domain/chart.rs:182`, `ios/Intrada/Views/Components/ChordChartEditSheet.swift:178`.

**3. A finished practice disappears when the local write fails, and the recovery copy goes with it**
Question 4. Verified by the lead. `SaveSession` pushes the session into the model, records success and clears the crash-recovery blob in the same command as the write; if the write comes back failed, the core reloads sessions from disk, which drops the pushed session, and the blob is already gone. The practice then exists nowhere and the musician sees one dismissable banner. The root is that `record_success` is called when a write is dispatched, not when the shell acknowledges it. Cost: a whole session (time, marks, passes, tempo, notes) lost, rare per write and total when it hits. Fix: clear the blob and record success only on the acknowledged write; on failure return to the summary so Save can be tapped again; rename `record_success` to say optimistic. Tier 3 and on the Fable list (the sensitive surfaces, named under The build order) (the blob lifecycle). Issue: #974, re-ranked from architecture to the top of the list: the issue says the summary is gone; the evidence says the recovery copy goes too. (CORE-1, BRIDGE-1, CORE-6)
Where: `crates/intrada-core/src/domain/session.rs:1728`, `crates/intrada-core/src/app.rs:222`, `crates/intrada-core/src/model.rs:99`.

**4. Once the musician dismisses the storage banner, later storage failures are never shown again, and one failure arm has no test**
Question 4. Verified by the lead; the test gap confirmed by mutation row 1. Dismissing the banner sets a mute that only `record_success` clears, and `surface_error`, used by the four persistence-failure arms alone, returns early while it is set; some sixty other sites write `last_error` directly, so a plain success clears the text but not the mute, and the next failed read or write leaves no trace in the ViewModel. Two faults compound it: `error_seq` bumps whenever any error is present after a handler rather than when a new one appears, so a success under a standing banner reads as a refusal in the shell; and deleting the surface call in the history-load arm fails no test. Cost: a musician practising against a failing store is told nothing until the next launch. Fix: one error path (every write through `surface_error`), the mute cleared on an acknowledged write, `error_seq` bumped only on a new error, and a test per failure arm. Tier 2. Issue: #1936. (CORE-2, CORE2-2, TEST-1, CORE-6)
Where: `crates/intrada-core/src/model.rs:87`, `crates/intrada-core/src/app.rs:135`, `:218`, the tests at `crates/intrada-core/src/persistence.rs:147`.

**5. A save the bridge refuses buzzes success and closes the form, and the confirmation it rests on has no test**
Question 4. Verified by the lead (the mechanism) and by range read (the counts); the line under Swift mutation was read by the lead. `Store.send` swallows a bridge throw after reporting it, so no effect, no render and no change to `errorSeq` follows, and every confirmation in the shell reads an unchanged `errorSeq`, or an absent `error`, as acceptance. That comparison lives in `Store.send(_:onSuccess:)`, which twelve sites use and no test covers (both sides are optional, so a nil ViewModel compares equal), and it is hand-copied fifteen more times; thirty-five call sites build a haptic generator directly because the helper offers no success or warning kind (#1451). Cost: the musician adds a piece, feels the buzz, watches the form close, and the piece is not there; rare, since it needs a bridge-level break such as the #846 class, but it lands on every mutate at once. Fix: `guarded` returns a distinct outcome that `send`, the helper and the form submit all treat as not confirmed; nil reads as not accepted; the helper gains the missing kinds and the copies move onto it; a fake-bridge test per branch. Tier 2, up a tier under the domain-sensitivity override because it touches the bridge contract. Issue: #1937. (SCREEN-1, TEST-2, SCREEN-7, and the second screens reviewer's extension)
Where: `ios/Intrada/Core/Store.swift:46`, `ios/Intrada/Core/Store+Feedback.swift`, `ios/Intrada/Views/Screens/ItemFormScaffold.swift:147`, `ios/Intrada/Views/Screens/FocusPlayerScreen.swift:219`, `ios/Intrada/Views/Screens/ProfileEditSheet.swift:182`.

**6. The crash-recovery blob was re-pinned without a key bump once already, so the guard #1116 relies on has failed in practice**
Question 4. Verified by range read: commit 884de62e (3 September, #1509) re-pinned the hex in `session.rs` and did not touch `Store.swift`, thirty-seven minutes after the pin was created; the two September shape changes (#1748, #1780) bumped the key correctly. Nothing mechanical ties the hex constant to `Store.sessionInProgressKey` (now v4); the failure message is the whole protocol. Cost: a blob from the previous build that decodes into a plausible wrong session, or a resume prompt that never appears; rare, unrecoverable when it lands. Fix: the blob version lives in the core (`ActiveSession::BLOB_VERSION`, exported over UniFFI), the shell builds the key from it, and the pin test asserts version and hex together. Tier 2, Fable list. Issue: #1116, re-ranked up with a demonstrated one-in-four miss and a mechanical fix; the issue's own keyed-JSON option would remove the class. (BRIDGE-2, TEST-6)
Where: `crates/intrada-core/src/domain/session.rs:6586`, `:6608`, `ios/Intrada/Core/Store.swift:21`.

**7. A tempo typed one digit too long is dropped and the item saves without it; four ranges are typed once in the core and again in a sheet**
Question 4. Verified by range read. The add and edit form parses the beats-per-minute field with `UInt16(...)`: "500" reaches the core and is refused with a message, while "99999" or a pasted non-number fails the Swift parse first, becomes no tempo at all, and the save succeeds with a buzz. The same shell-mirrors-core pattern holds four ranges twice: pass target 3 to 10, planned duration 60 to 3600 seconds written as 1 to 60 minutes (invisible to a grep for the constant), metre beats 2 to 12, score 1 to 10. Cost: entered data lost with a positive signal, rare; and a cap moved in the core silently disagrees with the control that sets it, certain the next time one moves. Fix: send the raw string or fault the form on an unparsable non-empty field (Tier 1); project the four ranges on the ViewModel and bind the controls to them (Tier 2, core first). Issue: #1512, re-ranked up: it read as tidiness, and one instance loses a value. (SCREEN-4, CORE2-6)
Where: `ios/Intrada/Views/Screens/ItemFormModel.swift:297`, `crates/intrada-core/src/validation.rs:15`, `ios/Intrada/Views/Components/EntrySettingsSheet.swift:27`, `ios/Intrada/Views/Components/ClickSheet.swift:105`, `ios/Intrada/Views/Components/ScoreSelector.swift:16`.
