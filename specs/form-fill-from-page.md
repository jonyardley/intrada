# Filling the add form from a scanned page, by the core's rules

> Tier 3 (a new plain call across the bridge). Issue #2229, part of epic #2220.
> Ships as two PRs: the core first, the iOS form in the same sitting. Plan: the
> comment on #2229, approved 3 October 2026 (1a, 2a).

## Problem

When a page is read, the add form decides for itself which fields take the
read: only an empty field, or one still holding an earlier read. It splits the
read tempo into the marking and the BPM boxes, and keeps each field's weak
mark. All of it lives in `ItemFormModel.fill` in Swift. The Android form
(#2220) would have to write the same rules again, and the two copies would
drift: a second copy that lets a rescan overwrite a typed title loses the
musician's work without a word.

## Decision 1: a plain call, asked on each read

The core does not hold the add form; the form is unsaved screen state until
Add is pressed. So the form asks on each finished read, as the key picker does
(#2226):

```rust
pub enum ReadField { Title, Composer, Marking, Bpm, Chart }

pub struct FieldNow { pub field: ReadField, pub text: String, pub holds_read: bool }
pub struct FieldFill { pub field: ReadField, pub value: String, pub weak: bool }

pub fn fill_form(draft: &PhotoDraft, fields: &[FieldNow]) -> Vec<FieldFill>
```

`fill_form` lives in `recognition.rs` beside `read_fields`. The shell stores
each returned value and its weak mark, and nothing else. Rejected: the core
holding the whole form as it is typed, which rebuilds the add form on both
apps for one rule and collides with 0.16's item and variation edits (#2245,
#2246, #2106).

## Decision 2: the draft crosses as the core's own bytes

The shell already holds the draft as the generated `PhotoDraft`, from
`PhotoRecognitionView.draft`. It hands it back serialised with the generated
bincode, exactly as events cross:

```rust
#[uniffi::export]
pub fn fill_form_from_read(
    draft: Vec<u8>,
    fields: Vec<FormFieldNow>,
) -> Result<Vec<FormFieldFill>, CoreError>
```

`FormReadField`, `FormFieldNow` and `FormFieldFill` are the UniFFI copies in
`ffi.rs`, as `WheelMode` is, since the core stays UniFFI-agnostic. The
`Form` prefix keeps the enum from being shadowed by `ItemFormModel`'s nested
`ReadField` in Swift, as `FormErrorField` was named for the same reason. Bytes that
do not decode return `CoreError::Bridge`, never a panic. Rejected: a hand
mirror of `PhotoDraft` and `Tempo` in `ffi.rs`, a second description of the
draft that could change apart from the first and break scanning silently.

## The rules

- A field takes the read when its text is blank after trimming, or when it
  still holds an earlier read. Whitespace alone now counts as blank, which the
  Swift `isEmpty` did not.
- A field the shell leaves out of `fields` is never written, so a forgotten
  field cannot overwrite typing.
- The tempo read fills the marking and the BPM separately, each by its own
  field's rule, both carrying the tempo's weak mark. The BPM is sent as its
  digits.
- A field the draft did not read is left out of the answer.
- The answer runs title, composer, marking, BPM, chart, whatever order the
  shell sent.

Typing taking a field's read mark off stays in the shell: it is the form
reacting to a keystroke, and the next `holds_read` it sends is the outcome.

## The two PRs

Core: `fill_form` and its tests, the UniFFI export and its tests, this spec,
the bindings regenerated by the build, and one Swift bridge test. No app
changes; nothing on screen changes.

Screens: `ItemFormModel.fill` sends the five fields and stores the answer; its
`replaceable` rule, the tempo split and the nested `ReadField` go, and
`readFrom` keys on `FormReadField`. `ItemFormReadFieldTests` stay as they are
and pass against the core's answer, plus one for a whitespace field. A draft
that cannot be serialised, or a `CoreError` from the call, fills nothing and is
reported through the store's bridge error path, so a wire drift (#846) reaches
the crash reports rather than scanning quietly stopping.

## Tests

Test first, in the core:

- Each of the five fields when blank, typed, holding a read, and whitespace.
- A typed field is never overwritten by a second read. Deleting the
  `holds_read` check fails the rescan rows, deleting the blank check the blank
  and whitespace rows; the typed rows are guarded by the take filter as a
  whole.
- A field missing from `fields` is not written.
- A tempo with only a marking, only a BPM, and both, against a typed marking.
- The weak mark per field, including the tempo's on both boxes.
- An empty draft answers nothing.
- Through the FFI call: a real draft's bytes decode and give the expected
  fills, and garbage bytes return an error. In Swift, a draft Swift encoded
  gives the expected fills, a weak one included.

## Out of scope

- The photo sheet and the read itself (`read_fields`).
- Key and notes: nothing on a page reliably says either.
- The Android form, which calls the same function when it is built.
